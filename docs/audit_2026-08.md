## Q1 — `brakeAllows()` 的调用点与单 broker 模式下的有效性

### 结论

`brakeAllows()` 在整个 `src/broker/broker.cpp` 中**只有 1 个调用点**,位于
`handlePublish()` 的「2. 向上传播」分支内,并且**被 `has_parent_` 保护**。

`brake_limit` / `brake_window` 对系统行为没有任何影响**。无论传 1、2、4 还是 1000,

## Q2 — 单 broker 模式的启动方式与 `has_parent_` 取值

## Q3 — `bench_broker.cpp` 里 `Heps` 的初始化方式与密钥路径

### 结论

`benchmarks/bench_broker.cpp` 调用的是 **`loadState()`,不是 `init()`**,加载路径为
`/tmp/dnspp_heps_full.key`。这个路径**与 `DnsMulticastBroker::initCrypto()` 写出的
`full_key_file` 完全一致**。

所以在「root broker 先启动并写完密钥、之后没有重启」的前提下,客户端和 broker 用的
**是同一把密钥**。但代码里**没有任何机制保证这个前提**:文件里没有版本号/指纹,
broker 每次启动都会重新生成并覆盖,`loadState()` 失败也不会终止进程。

### 证据

benchmark 端:

```
benchmarks/bench_broker.cpp:69-72
    Heps heps;
    if (encrypted) {
        heps.loadState("/tmp/dnspp_heps_full.key");
    }
```

broker 端写出的路径:

```
src/broker/broker.cpp:100-101
    std::string key_file = "/tmp/dnspp_heps.key";
    std::string full_key_file = "/tmp/dnspp_heps_full.key";

src/broker/broker.cpp:117-125
        // Save full state for clients (acting as HEPS proxy for blinding)
        std::ofstream ofs_full(full_key_file);
        ofs_full << mpzToHex(p.getN()) << "\n";
        ...
```

两处字符串逐字相同 → **路径一致**。`clients/test_client.cpp:42` 用的也是同一个路径。
全仓库只有这三处引用(`grep -rn "dnspp_heps" src clients benchmarks tests scripts`)。

`Heps::init()` 在生产代码中**从未被调用**,只有单元测试用:

```
$ grep -rn "\.init()" src benchmarks clients tests
tests/test_heps.cpp:8:    heps.init();
```

风险点 1 —— broker 每次启动都重新 keyGen 并覆盖文件,没有复用已有密钥的分支:

```
src/broker/broker.cpp:103-115

        Paillier p;
        p.keyGen(2048);          // ← 无条件重新生成
        he_n_ = p.getN();
        he_mu_ = p.getMu();
        ...
        std::ofstream ofs(key_file);   // ← 无条件覆盖
```

风险点 2 —— `loadState()` 失败只打印一行,然后正常返回,调用方也不检查返回值
(它是 `void`):

```
src/crypto/Heps.cpp:33-35
    } else {
        std::cerr << "Error: Could not load HEPS state from " << filename << std::endl;
    }
```

此时 `n_`、`mu_` 以及 `paillier_` 内部参数全为默认构造的 0。后续
`Heps::blindSubscription()` 第一步就是对 0 取模:

```
src/crypto/Heps.cpp:65-67
    mpz_class v = stringToMpz(name);
    mpz_class neg_v = (n_ - v) % n_;      // n_ == 0 → GMP 除零
```

**无法确定**该情况下的确切表现(未运行验证):GMP 对模 0 的行为是致命错误/abort,
所以最可能是崩溃而不是产出错误数据 —— 但这属于"碰巧崩了",不是设计上的 fail-fast。

风险点 3 —— 密钥文件是持久的 `/tmp` 文件,跨实验残留。若 bench 在 root broker 完成
2048 位 keyGen 之前就 `loadState()`,它会读到**上一次实验遗留的旧密钥**,而 broker 手里
是新密钥。这种情况下 `executeMatch()` 会用不匹配的 `n`/`mu` 做运算,结果几乎必然落在
`>= n/2` 分支,表现为「加密实验 recall 全为 0」或「delivered=0」,而不是任何报错。

### 影响

1. **路径一致,不存在"两把不同密钥"的静态 bug** —— 用户怀疑的这一条不成立。
2. 但正确性依赖**未被强制的启动顺序**。`README.md:200-202` 的手工两行命令没有任何
   同步(`&` 之后立刻起 bench),而 root broker 的 2048 位 keyGen 是秒级操作。
   `results/phase3/encrypted.log` 五个 trial 都是 `recall=1`,说明当时时序是对的;
   但这不是代码保证的,是运气。
3. `loadState()` 的失败路径违反 **I6(不静默降级)**。按 CLAUDE.md 的要求,
   读不到密钥必须 `exit(EXIT_FAILURE)`。
4. `bench_multi_broker` 完全不支持加密模式:它既不 `#include "crypto/Heps.h"`,
   `CMakeLists.txt:71-75` 也没有链接 `Paillier.cpp` / `Heps.cpp` 和 gmp。
   因此**目前不存在任何"多 broker + 加密"的实验通路**(这与 Q4/Q5 的结论互相印证)。

## Q4 — `child_active_` 的 key,以及加密模式下两个 key 能否相等

### 结论

- `handleSubscribe()` 中,`child_active_` 的 key 是**收到的 SUBSCRIBE 消息里的
  `SERVICE_NAME` 字段**(`*name`)。在加密模式下,子 broker 往上转发时填进这个字段的是
  **订阅侧盲化值 `bval_m1` 的十六进制串**。
- `handlePublish()` 向下传播分支中,查表用的 key 是 `pub_key`;在加密模式下它是
  **通告侧盲化值 `bval_n` 的十六进制串**。
- 这两个 key **不可能相等**。`bval_n` 与 `bval_m1` 是模 n² 下两个数学结构完全不同、
  且各自语义安全(带独立随机数)的值。因此**加密模式下向下传播分支永远查不到条目,
  publication 永远不会被转发给子 broker**。

### 证据

写入端(父 broker 收到来自子 broker 的 SUBSCRIBE):

```
src/broker/broker.cpp:213-229
void DnsMulticastBroker::handleSubscribe(const TlvMessage& msg, const struct sockaddr_in& client) {
    auto name = msg.getServiceName();
    if (!name) return;
    ...
    bool from_child = (flags & MsgFlags::FROM_CHILD);

    if (from_child) {
        std::string child_id = findChildByAddr(client);
        if (child_id.empty()) return;

        child_active_[*name].insert(child_id);      // ← key = SERVICE_NAME 字段
```

子 broker 往上转发时,`SERVICE_NAME` 填的是 `sub_key`,而 `sub_key` 在加密模式下就是
`bval_m1`:

```
src/broker/broker.cpp:249-252
    // Phase 3: Use blinded values as key if available
    auto bval_m1 = msg.getBlindedValue();
    auto bval_m2 = msg.getBlindedValueHi();
    std::string sub_key = (bval_m1 && he_enabled_) ? *bval_m1 : *name;

src/broker/broker.cpp:291-293
    if (has_parent_ && ot_parent_.find(sub_key) == ot_parent_.end()) {
        TlvMessageBuilder fwd(MsgType::SUBSCRIBE);
        fwd.addServiceName(sub_key); // Propagate the blinded key upwards
```

读取端(向下传播):

```
src/broker/broker.cpp:325-327
    // Phase 3: Determine pub_key
    auto bval_n_opt = msg.getBlindedValue();
    std::string pub_key = (bval_n_opt && he_enabled_) ? *bval_n_opt : *name;

src/broker/broker.cpp:355-357
    // 3. 向下传播
    auto child_it = child_active_.find(pub_key);
    if (child_it != child_active_.end()) {
```

两个值的数学来源(`src/crypto/Paillier.cpp:72-96`):

```
src/crypto/Paillier.cpp:72-87   blindNotification(x):
    mpz_class r_rand = rng.get_z_range(r_m);            // 每次调用新随机数
    mpz_class exp = (r_m * x + r_rand) * lambda;
    ... return (g^e_m * g^exp) mod n²

src/crypto/Paillier.cpp:89-96   blindSubscription(E_neg_v):
    mpz_class exp = r_m * lambda;
    ... return (g^d_m * E_neg_v^exp) mod n²
```

推理:
1. 两者用的指数分量互为相反数(`e_m` vs `d_m = n - e_m`,见 `Paillier.cpp:36-37`),
   构造上就是为了在 `match()` 里相乘抵消 —— 它们**被设计成不相等**,相等才是异常。
2. `blindNotification` 每次调用都掺入新的 `r_rand`(`Paillier.cpp:77`),`blindSubscription`
   的输入 `E_neg_v` 来自 `Paillier::encrypt()`,后者也每次取新随机数
   (`Paillier.cpp:52`)。两者都是语义安全的密文,取值域是 ~4096 位的 Z_{n²}。
3. 因此 `bval_n == bval_m1` 的概率是可忽略的(≈ 2^-4096),工程上视为**永不相等**。

顺带:明文模式下两个 key 都退化成 `*name`,所以能对上 —— 这就是 `results/phase2/`
(纯明文)看起来正常、而加密路径从未被这条实验验证过的原因。

### 影响

1. **加密模式下的层级路由是断的**:父 broker 即使收到了带盲化值的 publication,也不会
   向任何子 broker 转发。`stat_forward_down` 在加密多 broker 场景下恒为 0。
2. 这同时违反不变量 **I4(密文不能当索引键)**:`child_active_`、`subscribers`、
   `pub_cache`、`brake_count`、`last_active`、`ot_parent_` 六张表在加密模式下全部以
   密文为 key(`broker.h:77-82`)。除了对不上,还会导致每条订阅/通告都落进新桶 →
   `pub_cache` / `ot_parent_` 无界增长,`cleanupExpired()`(`broker.cpp:523-536`)
   按 `subscribers` 的 key 清理,也清不掉 `child_active_` 与 `ot_parent_`。
3. 论文中任何关于「加密层在多 broker 树上的开销/recall」的论断,当前代码都不支持。
   仓库里也确实没有这类数据(`results/phase3/` 只有单 broker 的 plain/encrypted)。

## Q5 — 向父 broker 转发 SUBSCRIBE 时携带的字段,以及父 broker 的 HE 投递

### 结论

向父 broker 转发的 SUBSCRIBE **只有三个 TLV:`SERVICE_NAME`、`COORDINATES`、`FLAGS`**。
**不含 `BLINDED_VALUE`,也不含 `BLINDED_VALUE_HI`。**

父 broker 收到后,因为带 `FROM_CHILD` 标志,会走 `from_child` 分支并**提前 return**,
根本不会为这条订阅创建 `GeoClient` —— 也就是说 `gc.blinded_m1` **这个对象不存在**。
即使假设它走到了普通分支,由于消息里没有盲化 TLV,`gc.blinded_m1` 也会是**空字符串**。

结合 `handlePublish()` 加密投递循环里的 `if (gc0.blinded_m1.empty()) continue;`:
**父 broker 在加密模式下无法向任何来自子 broker 的订阅投递 publication。**

### 证据

## Q6 — `initCrypto()` 写出的密钥文件、私钥材料与文件权限

### 结论

`initCrypto()` 一共写出 **2 个文件**:

| 文件 | 内容(每行一个十六进制数) | 性质 |
|---|---|---|
| `/tmp/dnspp_heps.key` | `n`, `mu` | 分发给 leaf broker,注释称"public key" |
| `/tmp/dnspp_heps_full.key` | `n`, `mu`, `lambda`, `e_m`, `d_m`, `r_m` | 分发给客户端,**含完整私钥材料** |

其中 **`lambda`、`e_m`、`d_m`、`r_m` 全部是私钥/盲化密钥材料**,四个全在第二个文件里。
`mu` 是 Paillier 的解密辅助量(教科书定义中属私钥),这里因为 broker 做 `Match` 必须用到
它而被下发,单独持有 `mu`(无 `lambda`)不足以解密。

两个文件都用裸 `std::ofstream` 创建,**代码里没有任何 `chmod` / `umask` 调用**,
因此权限是 `0666 & ~umask`,在典型环境下为 **0644(全局可读)**。

**root broker 确实持有完整私钥**:它自己生成全部参数,并把它们写进一个它随时可以再读回来的
世界可读文件。仓库中不存在独立的 HEPS 进程 —— root broker 就是 HEPS。

## 优先级建议

排序依据:**对论文结论的杀伤力** > 对系统功能的杀伤力 > 工程卫生。

### P0 — 会让已发表/待发表的结论直接失效,必须在交稿前处理

**P0-1 · Q6:root broker 兼任 HEPS 并持有完整私钥(世界可读)**
杀伤对象:论文的**核心研究贡献**(隐私)。这不是"实现细节有瑕疵",而是被评测的那个
安全属性在实现里不成立。修复方向二选一,但必须在论文里明说:
(a) 把 HEPS 拆成独立进程,broker 只拿 `n`、`mu`;或
(b) 保留现状但在论文的 threat model 一节显式声明「本原型中 root broker 与 HEPS 同址,
因此仅评估性能开销,不主张隐私保证」。文件权限无论如何都应改成 0600。

**P0-2 · Q1:brake 在单 broker 模式下完全不执行**
杀伤对象:`README.md:279-290` 的 Phase 1 brake sweep 整表 + `results/phase1/` 全部数据。
这批数据是 Phase 1 语义(brake 门控本地投递)的产物,Phase 2 的 `bd5c2cc` 把调用点搬进了
`has_parent_` 分支却没有重跑,也没有更新文档。当前代码重跑会得到四组相同的数字。
需要决定:是恢复单 broker 的 brake 语义并重跑,还是删掉 Phase 1 那张表、只保留 Phase 2
(多 broker)的 brake 结论。**在做出决定前,不要把 Phase 1 的表放进论文。**

**P0-3 · Q4 + Q5:加密模式下的跨 broker 路由完全不通**
杀伤对象:任何「加密 + 多 broker」的实验(目前尚不存在,所以没有已发表数据受损,
但它封死了一整条评测路线)。两个缺陷需要一起修才有效:
(i) 转发 SUBSCRIBE 时带上 `BLINDED_VALUE` / `BLINDED_VALUE_HI`,并让父 broker 为子 broker
的订阅建立可投递的表项;(ii) 给路由表换一个与密文分离的稳定 key(**I4**)。
建议把 (ii) 作为设计前提先定下来,否则 (i) 修完仍然对不上。

### P1 — 让 P0 长期未被发现的根因,应尽快修

**P1-1 · Q2:`run_integration_test.sh` 目前跑不通,且 broker/client 的 CLI 都已变更**
脚本在 Paris 发布那一步就被 `set -e` 终止,断言部分永远执行不到。它本应是 Q1 这类
行为退化的门禁。修复成本低(改三行调用),收益是后续每次改动都有回归保护。
同时应修正 `README.md:200-202` 的启动命令。

**P1-2 · Q3 + Q6:所有密钥/配置读取路径的静默降级(I6)**
`parseConfig()` 打不开文件走默认值、`Heps::loadState()` 失败只打印一行、leaf broker
读不到密钥退回明文 —— 三处都应改成 fail-fast。这是 CLAUDE.md 明确点名的坏模式,
也是「一次失败的加密实验看起来像一次成功的实验」的直接来源。
配套建议:密钥文件加一个指纹/版本行,broker 启动日志里打印它,客户端加载后校验。

### P2 — 工程卫生,不阻塞交稿但应记录进论文的 limitations

**P2-1 · I4:六张路由表在加密模式下全部以密文为 key**

`executeMatch()` 没有调用计数器,`he_enabled_` 虽然打进了启动日志

**P2-3 · I8:文档与代码的其他不一致**
`CLAUDE.md` 写的是 `src/broker/main.cpp`,实际在 `src/main.cpp`;
`docs/learning_log.md` 把 HEPS 描述为独立可信第三方;
`README.md` 的 brake 表见 P0-2。
